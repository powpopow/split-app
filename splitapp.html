grand total shown in Review screen with optional receipt comparison (✓/⚠) - Tracks running balance (who owes whom, and how much) — perspective flips per user - History with bill detail view (edit + delete) - Summary view - Google sign-in: each user identified by email; perspective-aware home, balance, and item order - Home screen: stacked avatars — tap back avatar to instantly switch perspective - PWA-ready: can be added to iOS/Android home screen and launches without browser UI - All data stored in Google Sheets (source of truth); local localStorage cache for fast load ## Tech stack | Layer | Choice | |---|---| | Frontend | Single HTML file, plain JS/CSS, no framework | | Hosting | GitHub Pages (`powpopow.github.io/split-app/splitapp.html`) | | OCR | Gemini Vision API (dynamic model selection, auto-fallback) | | Backend | Google Apps Script Web App (POST = write, GET = read) | | Database | Google Sheets (Bills tab + Config tab) | | Local cache | localStorage (fast load, syncs from Sheets on startup) | ## Architecture ``` [Phone camera] ↓ [Gemini Vision API] ← key stored in Config tab of Google Sheet ↓ [Manual entry form] ← OCR pre-fills this; Dark/light contrast with the teal PP avatar. - **Orange-brown for Pat's chip** — warm complement to teal. Avoids red (too alarming for expense assignment) and blue (too similar to teal). - **Minimal card UI** — each section is a white card on light gray. Reduces visual noise, easy to scan. - **No gradients or heavy shadows** — keeps the app feeling light and fast. The balance card uses a flat teal fill, not a gradient. - **Uppercase section labels** (`RUNNING BALANCE`, `RECENT BILLS`) — small caps treatment adds structure without heavy typography. - **Bottom nav with teal + button** — standard mobile app pattern. The + is oversized and teal to make adding a bill the primary action. ## Key design decisions **Why single HTML file?** Easy to host on GitHub Pages with zero build step. Anyone can view source, copy, deploy. **Why Google Sheets as database?** Both users can view/edit data directly in Sheets without needing a separate admin UI. Free, reliable, no server to maintain. **Why Apps Script as backend?** Runs inside Google's infrastructure, free tier is sufficient, no auth tokens needed for the app itself. **Why dynamic Gemini model selection?** Gemini models get deprecated (happened with `gemini-2.0-flash` in March 2026 — quota went to 0). Dynamic selection queries available models at runtime so the app never breaks due to model retirement. **Why OCR → manual form (v1.4.0)?** Original design jumped OCR straight to Review & Assign, which meant: (a) no who-paid selection, (b) no item editing, (c) blank screen on failed OCR. Sending OCR output to the manual form first lets the user review/fix before proceeding. **Why "Shared" not "50/50"?** "50/50" is mechanical and less intuitive. "Shared" communicates the intent — both people share this item equally — without requiring the user to think in percentages. **Why assignment chip = cycle + dropdown (v1.8.5)?** A single button that only cycles forces the user to tap multiple times to reach the option they want. A split chip (left = fast cycle, right ▾ = full dropdown) keeps the fast path and adds discoverability without cluttering the item row. Cycle order is perspective-aware (current user first after Shared) so the most-used assignment is always one tap away. **Why perspective-aware UI?** Both users see the same data but from opposite sides: balance direction, item assignment cycle order, greeting all flip based on `currentUser`. This avoids confusion ("does positive balance mean I owe or I'm owed?") and makes the app feel personal to each person. **Why stacked avatars on home (v1.9.0)?** Two flat avatars side by side suggested they were equal buttons. Stacking communicates "you are here" (front) vs "switch to them" (back) — a natural spatial metaphor. Tapping the back avatar is a perspective switch, not a sign-out. **Why no settlement flow?** A dedicated settlement screen adds complexity for a rare action. Users can record a settlement as a normal bill: one item "Settlement [amount]", assign entirely to the person who owes, paid by the settler. The balance adjusts correctly with no extra code. **Why ignore 429 errors from Gemini model probe?** The model probe at startup occasionally gets rate-limited (429). This is cosmetic — it doesn't affect the actual OCR calls or the API quota. Adding retry logic adds complexity for no real user benefit. --- > **Note:** Bugs and planned features are tracked live in `splitapp-backlog.md`.
